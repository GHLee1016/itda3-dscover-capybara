# ITDA 3rd 학술제 제출 저장소 - DScover_카피바라

OCR 기반 상품 소비기한 정보 추출 아키텍처. 자세한 설계 논리는 `[DScover_카피바라]_아키텍처구조도.pdf` (이메일 제출본)를 참고하세요.

## 1. 요약

- **입력**: 상품 뒷면 이미지 (`ITDA_INPUT_DIR` 환경변수로 경로 주입)
- **출력**: `submission.csv` (`ITDA_OUTPUT_PATH` 환경변수 경로에 저장)
- **엔진**: EasyOCR (`ko`+`en`, CPU, 오프라인) + 정규식/키워드 기반 날짜 후보 스코어링
- **핵심 설계**: 1) classical CV 후보 검출 + 배치 인식(1단계) → ROI 재시도(2단계) → 시간이 남을 때만 전체 재검출(3단계)의 3단계 구조, 2) 4-core 병렬처리, 3) 명시적 안전 마진(250초) 기반 시간 예산 가드레일, 4) 연-월-일뿐 아니라 해외 제품의 일-월-년/월-일-년/영문 월이름 표기도 국가 추정 없이 판별, 5) 2자리 연도 표기(`22.10.21`)와 필드 일부만 깨진 날짜(`2025.05.0` → `2025-05-NONE`)도 부분점수를 살려 회수
- **실측 검증**: 실제 4-core Codespaces 환경에서 3,352장과 실제 평가 규모인 500장 두 스케일 모두 완주 확인. 최종 버전은 **500장 938.4초 / 값이 채워진 행 171장(34.2%)** 으로, 2,400초 컷오프까지 약 1,460초(61%)가 그대로 남는다

## 2. 실행 방법

### 1) 환경 구축

```bash
git clone <본인 팀 저장소 URL>
cd itda3-dscover-capybara
pip install -r requirements.txt
```

macOS 사용자는 `requirements.txt` 상단의 `+cpu` 접미사를 제거하고 설치하세요.

### 2) 가중치 다운로드 (인터넷 필요, 1회)

```bash
bash download_weights.sh
```

`weights/craft_mlt_25k.pth`, `weights/korean_g2.pth` 두 파일을 GitHub Release Assets(공식 EasyOCR 저장소)에서 내려받습니다. 이 스크립트는 predict.ipynb 실행 **전에** 1회만 실행하면 되며, predict.ipynb 자체는 `download_enabled=False` 로 동작하여 실행 중 어떤 네트워크 요청도 하지 않습니다.

### 3) 채점 재현성 검증 (운영진 표준 명령어)

```bash
export ITDA_INPUT_DIR=./val_images
export ITDA_OUTPUT_PATH=./submission.csv

jupyter nbconvert --to notebook --execute predict.ipynb \
    --ExecutePreprocessor.timeout=2400 \
    --output /tmp/executed.ipynb
```

오프라인(네트워크 차단) 상태에서도 위 명령이 에러 없이 완료되고 `submission.csv` 가 생성되는지 반드시 확인하세요.

## 3. 아키텍처 설계 논리 (요약)

상품 뒷면에는 소비기한 외에도 제조일자, 바코드, 품목보고번호, 전화번호, 영양성분, LOT 번호 등
날짜와 혼동될 수 있는 숫자가 다수 존재한다. 동시에 채점 환경은 CPU 전용·오프라인·2400초
타임아웃이라는 강한 제약을 가진다.

이 아키텍처는 두 번의 재설계를 거쳤다. 로컬(2-core) 프로파일링만으로는 실제 4-core 채점
환경의 비용 구조를 정확히 예측할 수 없다는 것을 직접 겪었기 때문에, 그 과정을 그대로 남긴다.

**1차 재설계 (로컬 프로파일링 기반, 이후 실제 환경에서 재검증되어 뒤집힘)**: 최초에는
"1단계 classical CV로 저비용 후보 검출 → 실패 시에만 2단계 EasyOCR 전체 파이프라인 fallback"
구조였다. 로컬 2-core에서 150장/60장 표본을 프로파일링한 결과 1단계 적중률이 8~10%에 불과한
반면 처리 시간은 2단계와 비슷해(1.6~1.7초/장), 이미지의 90% 이상이 두 단계 비용을 모두
지불하면서도 이득이 작다고 판단해 1단계를 제거하고 EasyOCR 단일 패스(canvas=550)로
단순화했었다.

**2차 재설계 (실제 4-core 환경 검증 후)**: 실제 채점 환경과 동일한 GitHub Codespaces 4-core
인스턴스에서 전체 3,352장을 직접 실행해보니 위 결론이 뒤집혔다. classical CV 후보 검출을
없애지 않고, 대신 후보 수를 34→16개로 줄이고 실패 시 이미지 전체를 다시 검출하는 대신
상위 6개 후보만 재인식하도록 가볍게 만든 버전이 **전체 3,352장을 1,475.5초 만에 처리하고
(예산 2,250초의 66%만 사용) 성공 378장(11.28%)**을 기록했다 — 이전 단일 패스 방식(9.37%,
게다가 54%만 처리하고 나머지는 시간 초과로 NONE)보다 정확도·커버리지 모두 우수했다. 즉
로컬 2-core와 실제 4-core에서 "classical CV 재사용이 저렴한가"에 대한 결론 자체가 달랐다.
다만 이 방식은 classical CV가 애초에 후보 박스를 놓친 이미지는 구조적으로 복구하지 못한다는
한계가 있었고(로컬 100장 재현 시 확인된 사례: 성공했어야 할 이미지가 이 방식에서는 NONE),
동시에 예산의 34%가 그냥 남는다는 것도 확인됐다. 이에 아래처럼 **3단계 구조**로 다시 합쳤다.

1. **1단계 (classical CV 후보 검출 + 배치 인식)**: 형태학적 연산으로 텍스트 줄 후보를 최대
   16개(`FAST_MAX_BOXES`) 찾고, EasyOCR 검출기(CRAFT)는 생략한 채 인식기만 원본 해상도로
   한 번에 배치 호출한다(`reader.recognize(..., batch_size=...)`). 실제 4-core 환경에서
   대부분의 이미지를 이 단계만으로 매우 저렴하게 처리한다.
2. **2단계 (ROI 재시도)**: 1단계가 실패하면, 이미지 전체를 다시 검출하지 않고 1단계가 찾은
   후보 중 상위 6개(`ROI_RETRY_BOXES`)만 CLAHE로 대비를 보정해 재인식한다. 여전히 저비용이다.
3. **3단계 (전체 재검출, 시간이 남을 때만)**: 1·2단계 모두 실패하면 — classical CV가 애초에
   후보 박스 자체를 놓친 경우라 2단계로는 복구 불가능하다 — **명시적 안전 마진
   (`SAFETY_MARGIN_SEC`=250초)을 침범하지 않는 한도 내에서만** CLAHE + EasyOCR 전체 파이프라인
   (검출+인식)을 다시 시도한다. "워커 1개가 이미지 1장에 쓸 수 있는 여유시간"
   (`(남은 시간×N_WORKERS)/남은 이미지 수`)이 클수록 큰 canvas(550px)를, 작을수록 작은
   canvas(250px)를 쓰고(`TIER3_CANVAS_SCHEDULE`), 그마저 안 되면 3단계를 생략해 NONE으로
   남긴다. 로컬 100장 재현 테스트에서 이 3단계가 1·2단계만으로는 놓쳤던 이미지를 실제로
   복구하는 것을 먼저 확인했다(성공 17→30장으로 증가). 이후 실제 4-core 환경에서 전체
   3,352장으로 최종 검증했고, **1,892.8초 만에 완주(안전 마진 미침범)하고 정답 407장(12.14%)**을
   기록해 1·2단계만 쓴 버전(378장, 11.28%)보다 29장을 추가로 복구했다.
4. **후보 스코어링**: 정규식(`YYYY.MM.DD`, `YYYY-MM-DD`, `YYYY년MM월DD일`, 콤마 오인식 보정,
   구분자 없는 `YYYYMMDD` 등)으로 날짜 형식 후보를 모두 추출하고, 달력 기준 유효성 검사
   (`datetime.date`)로 `2026-02-30`처럼 실존하지 않는 날짜를 제외한 뒤, 같은 줄/인접 줄에
   `소비기한`, `유통기한`, `까지` 가 있으면 가점, `제조일자`, `제조`, `LOT`, `PROD.`, `MFD` 가
   있으면 감점하여 최고 점수 후보를 최종 날짜로 채택한다. 서로 다른 박스로 쪼개진 날짜 조각은
   좌표 기반으로 이어붙여(stitching) 재시도한다.
5. **4-core 병렬 처리**: `concurrent.futures.ThreadPoolExecutor` 로 이미지 단위 작업을 워커
   스레드에 분배한다. 각 스레드는 최초 호출 시 자신만의 EasyOCR Reader 를 한 번만 로드해
   재사용하며, 프로세스 전체의 BLAS/torch 스레드 수를 1로 고정해(oversubscription 방지)
   워커 수만큼만 코어를 활용한다. `multiprocessing.Pool(fork)` 는 개발 초기에 사용했으나,
   Jupyter 커널(ipykernel)이 이미 여러 백그라운드 스레드를 띄운 상태에서 `fork()` 하면 자식
   프로세스가 락 획득에 실패해 멈추는 사례가 있어 스레드 기반으로 교체했다. 3단계의 여유시간
   계산도 "남은 이미지 수"라는 워커 간 공유 상태가 필요한데, 스레드는 메모리를 공유하므로
   락(`threading.Lock`)으로 보호한 카운터 하나만으로 구현할 수 있었다.
6. **명시적 안전 마진 정책**: "시간이 남으면 정확도에 재투자한다"는 방향을 계속 밀고 나가되,
   `SAFETY_MARGIN_SEC=250초`는 어떤 경우에도 침범하지 않는 하드 하한선으로 둔다. 1·2단계는
   항상 시도하고, 3단계만 이 마진 안에서 남는 시간만큼 적응적으로 수행한다 — 정확도를
   더 올리려는 시도가 "타임아웃으로 정량 0점"이라는 최악의 결과로 이어지지 않도록 하는
   구조적 장치다.
7. **정밀도 우선(NONE 허용) 전략**: 키워드/형식 근거가 불충분한 경우 억지로 추정하기보다 `NONE`
   을 반환하도록 설계했다. 잘못된 날짜를 자신 있게 제시하는 것보다, 근거가 있는 경우에만 값을
   내는 편이 더 신뢰할 수 있는 시스템이라고 판단했기 때문이다.
8. **해외 제품 대응(날짜 표기 순서 판별)**: 3,352장 중 무작위 표본 검수 결과, 국내 표기
   (연-월-일)가 아닌 해외 수입 제품의 날짜(예: `EXP. DATE: 11/05/2021`, `EXP:DEC-28-2021`)가
   20장 중 5장(25%) 꼴로 섞여 있는 것을 확인했다. 이를 위해 연도가 뒤에 오는 숫자형 패턴과
   영문 월 이름 패턴(`JAN` ~ `DEC`)을 추가했다. 핵심은 **국가·언어를 추정하지 않고 값 자체로만
   순서를 역산**하는 것이다(`_resolve_month_day`) — 두 숫자 중 하나가 13 이상이면(=달이 될 수
   없음) 그게 일(day)로 확정되고 나머지가 월이 되며, 이는 일-월-년(유럽식)이든 월-일-년
   (미국식)이든 국가와 무관하게 항상 성립하는 산술적 사실이라 국가 판별이 필요 없다. 두 숫자가
   같으면(예: `09/09/2021`) 어느 순서로 읽어도 결과가 같으므로 애매하지 않다. 그 외에 두 숫자
   모두 1 ~ 12 범위라 순서를 판별할 근거가 없는 경우에는 — 이때도 정밀도 우선 원칙을 그대로
   적용해 — 억지로 추정하지 않고 연도만 채택하고 월/일은 `NONE`으로 둔다(항목 12 참고). 이
   과정에서 `제조일자`에 해당하는 `PROD.`/`PROD DATE`/`MFD` 같은 영문 표기도 감점 키워드에
   추가해, 제조일자가 소비기한 자리를 잘못 차지하지 않도록 했다. 정규식/스코어링 로직만
   격리한 17개 단위테스트(실제 표본에서 발견한 해외 표기 5종 포함, 오탐 위험이 있는 바코드·
   영양정보·전화번호·주소 5종 포함)로 회귀와 오탐 여부를 먼저 검증했고, 이후 500장 실제
   실행(항목 "재설계 검증 방법" 참고)에서 이 로직이 실제로 5건 발동한 것을 CSV로 직접
   확인했다.
9. **바코드(EAN-13) 국가 힌트**: 항목 8의 값 기반 순서 판별로도 여전히 애매한 경우(두 숫자
   모두 1 ~ 12 범위)에 한해, 제품에 인쇄된 EAN-13 바코드의 GS1 국가 접두어로 "그 나라가
   관용적으로 쓰는 날짜 표기 순서"를 마지막 힌트로만 참고한다. 국가/언어 자체를 인식하는
   것이 아니라(EasyOCR이 `ko`/`en`만 지원해 신뢰할 수 없다고 이미 판단했다), 바코드 숫자
   패턴만 보는 것이라 인식 언어와 무관하게 동작한다. 임의의 13자리 숫자(전화번호, 신고번호
   등)를 바코드로 오인하지 않도록 EAN-13 체크섬 검증을 통과한 숫자열만 인정한다. 접두어
   000-139/754-755(미국·캐나다)는 월-일-년, 200-899 대부분(유럽·중남미·중동·아프리카 등)은
   일-월-년으로 매핑했고, 접두어 880(한국)·450-459/490-499(일본)·690-699(중국)는 이미
   연-월-일 표기라 이 힌트 자체가 필요 없으므로 `None`으로 둔다. **이 힌트는 항목 8에서 이미
   확정 가능한 날짜(>12 규칙, 월 이름 패턴, 연-월-일 패턴)를 절대 덮어쓰지 않고**, 정말
   마지막까지 애매한 잔여 케이스에만 관여하도록 설계해 정밀도 우선 원칙을 유지했다. 표본
   검수에서 발견한 실제 바코드로 검증했다: `000880.jpg`의 실제 바코드(`5202175019831`,
   그리스 접두어 520)를 넣으면 애매했던 `EXP. DATE: 11/05/2021`이 일-월-년 힌트로
   `2021-05-11`로 확정되는 것을 단위테스트로 직접 확인했다. 체크섬이 유효하지 않은 13자리
   숫자열은 힌트로 쓰이지 않는 것, 이미 확정 가능한 날짜는 바코드 힌트와 무관하게 그대로
   유지되는 것도 함께 검증했다(아래 단위테스트 6종 추가, 총 23개 전부 통과). 다만 이 기능은
   **아직 500장 실제 채점 규모로 재실행해 발동 건수를 직접 세어보지는 못했다** — 표본에서
   발견한 애매 사례 자체가 드물어(20장 중 실질적 애매 사례 1 ~ 2건) 기대 효과는 크지 않지만,
   단위테스트로 안전성(오탐 없음, 우선순위 미침범)은 확인된 상태다.
10. **2자리 연도 표기 대응**: 실제로 `NONE`이 나온 이미지 84장을 직접 열어 OCR이 무엇을
    읽고 있는지 전수 조사한 결과, **OCR은 날짜를 정확히 읽었는데 정규식이 4자리 연도
    (`20\d{2}`)만 받아서 버리는** 사례가 있었다(예: `22.10.21`, `21.06.13`). 원본 이미지를
    눈으로 확인해 실제 인쇄된 값임을 검증했다. 2자리 숫자 3개는 무게·가격·로트번호와 형태가
    겹쳐 오탐 위험이 크므로 ① 구분자가 `.`/`-`/`/` 중 하나로 분명히 있을 것(공백·콤마 구분
    제외), ② 어느 자리를 연도로 읽든 2020 ~ 2035 범위일 것, ③ 달력상 실존하는 날짜일 것을
    모두 만족할 때만 후보로 인정하고, **4자리 연도 패턴이 하나도 없을 때만** 쓴다.
    순서 해석은 YY.MM.DD / DD.MM.YY / MM.DD.YY 세 가지를 모두 시도해 유효한 것만 남기는데,
    유효한 해석이 하나뿐이면 그것으로 확정하고(예: `20.12.14`는 맨 뒤 14를 연도로 읽으면
    2014년이 되어 범위를 벗어나므로 YY.MM.DD 하나만 남는다), 둘 이상이면 항목 9의 바코드
    국가 힌트로 고르고 힌트가 없으면 국내 관례인 YY.MM.DD를 택한다(데이터셋이 국내 유통
    상품 사진이므로). 추가로 **날짜 바로 뒤에 `시:분`이 붙어 있으면 생산 타임스탬프로 보고
    제외**한다 — 실제 이미지 `001540`에서 `20.12.14 22:54`(제조 시각)와 `21.06.13`(소비기한)이
    함께 찍힌 사례를 발견했고, 이 규칙이 없으면 제조 시각을 소비기한으로 잘못 내보낸다.
    콜론이 `,`나 `*`로 오인식되는 실측 사례가 있어 그 변형도 시각 구분자로 인정한다.
11. **부분 구제(필드 단위 살리기)**: 연-월-일 형식은 분명한데 일부 필드만 OCR 오인식으로
    달력 검증에 실패하는 사례가 실패 이미지에서 여러 건 관측됐다(실측: `2025.05.0` 일 잘림,
    `2026.01,00` 일이 00, `2025.71.10` 월이 71, `2025.03.39` 일이 39). 기존에는 이런 후보를
    통째로 버려 `NONE-NONE-NONE`이 됐지만, **채점이 연/월/일 필드별 부분점수**이므로 왼쪽부터
    검증되는 필드까지만 살려 `2025-05-NONE` / `2025-NONE-NONE` 형태로 내보낸다. 빠진 값을
    추측하는 것이 아니라 "검증된 필드만" 내보내는 것이라 항목 7의 정밀도 우선 원칙과
    어긋나지 않는다. 깨진 필드의 **오른쪽은 자릿수 밀림 가능성이 있어 그 자체로 유효해
    보여도 신뢰하지 않는다**(그래서 `2025.71.10`은 일(10)을 버리고 `2025-NONE-NONE`).
    후보 선택 순서는 **키워드 점수(소비기한/제조일자 구분)가 항상 최우선**이고, 점수가 같을
    때만 근거 강도(4자리 완전 날짜 > 2자리 연도 > 부분 후보)로 동점을 가른다 — 근거 강도를
    키워드보다 앞세우면 "제조일자는 깨끗하게 읽히고 소비기한은 일부만 읽힌" 라벨에서
    제조일자를 답으로 내보내게 되기 때문이다(단위테스트로 이 회귀를 고정해 두었다).
12. **출력 포맷: 부분 인식 정책**: `final_date`는 연/월/일 중 확실한 필드만 채우고 나머지는
   `NONE`으로 표시한다 — 연/월/일이 모두 불명확하면 `NONE-NONE-NONE`, 위 항목 8처럼 연도만
   확실하고 월/일 순서가 애매하면 `2021-NONE-NONE`(500장 실행에서 5건 확인), 항목 11처럼
   연·월은 확실하고 일만 깨졌으면 `2025-05-NONE` 형식이다. 연도만 불명확하고 월/일이
   확실한 `NONE-10-14` 형식은 운영진이 제시한 예시 포맷이지만, "알려진 한계"에 적어둔 대로
   연도 없이 월/일만 있는 케이스 자체를 아직 별도로 추출하지 않아 현재 코드에서는 발생하지
   않는다(연도가 확인되지 않으면 그 뒤 필드도 신뢰하지 않는다). 제출 안내서의 스키마 표 예시(전체 미인식 시
   `final_date=NONE`,
   하이픈 없는 단일 값)와 운영진이 이후 공지한 문구(&quot;연월일이 다 부재할 경우
   NONE-NONE-NONE 형식으로&quot;)가 서로 다른데, 운영진 채점이 팀이 문서화한 규칙을 기준으로
   애매한 값을 판단한다고 명시했으므로, 본 팀은 **이후 공지 문구(`NONE-NONE-NONE`)를 최종
   기준으로 채택**했다는 점을 여기에 명시적으로 남긴다.

### 재설계 검증 방법 (재현 가능)

로컬 프로파일링(2-core)과 실제 채점 환경(4-core Codespaces)의 결론이 서로 달랐던 경험 때문에,
이 저장소의 최종 구조는 로컬 표본 추정에만 의존하지 않고 **실제 4-core 환경에서 전체 3,352장을
완주시킨 결과**를 기준으로 확정했다. 검증은 두 단계로 진행했다: (1) 1·2단계만 있는 버전을
실제 4-core에서 먼저 돌려 1,475.5초·정답 378장(11.28%)을 확인해, 로컬 프로파일링이 내린
"classical CV 1단계는 제거하는 게 낫다"는 결론을 뒤집을 근거로 삼았다. (2) 이후 3단계까지
포함한 최종 구조를 같은 실제 4-core 환경에서 전체 3,352장으로 다시 실행해 **1,892.8초 만에
완주(안전 마진 250초 미침범)하고 정답 407장(12.14%)**을 확인했다 — 1·2단계만 쓴 버전보다
29장을 추가로 복구했고, 2,150초 예산 대비 257초, 2,400초 컷오프 대비로는 507초가 그대로
남아 타임아웃 위험이 전혀 없었다. 로컬에서는 같은 100장 테스트셋으로 (a)(b) 버전을 직접
실행해 성공 건수(17→30장)와 극단적으로 짧은 시간 예산(40초)에서도 안전 마진을 넘기지 않고
완주하는지를 사전 검증했다.

**(3) 실제 평가 규모(500장) 재검증**: 3단계의 canvas 선택 공식이
`(남은시간×N_WORKERS)/남은이미지수`로 이미지 수에 반비례하기 때문에, 실제 평가셋(500장,
운영진 공지 기준)에서는 3,352장 전체를 쓴 위 검증보다 장당 배정되는 여유시간이 약 6.7배
커져 3단계가 훨씬 더 자주 걸릴 것으로 예상됐다. 이 가설이 실제로 맞는지, 그리고 2,400초
컷오프를 여전히 안전하게 지키는지를 확인하기 위해 3,352장 중 500장을 무작위(seed=42)로
뽑아 같은 4-core Codespaces에서 **채점 명령을 그대로 재실행**했다. 결과: **981.8초에 완주
(2,400초 대비 약 1,400초/59% 여유, 2,150초 소프트 예산에도 못 미쳐 안전마진 로직이 아예
발동하지 않음)하고 성공 141/500장(28.2%, 이 중 136장은 연/월/일 전부 확정, 5장은 항목 8의
해외 표기 순서-애매 로직이 실제로 발동해 연도만 확정)**을 기록했다. 3,352장 스케일 검증
(12.14%)보다 훨씬 높은 수치인데, 이미지당 여유시간이 커진 만큼 3단계가 더 큰 canvas로
더 자주 걸린 결과로 해석된다 — 즉 **500장 스케일에서 나온 이 수치가 실제 채점 시 나올
값에 더 가깝다.** `submission_500.csv` 결과를 직접 검수해 image_id 중복·연도 범위 이상치가
없음도 확인했다.

**(4) 실패 이미지 전수 조사 기반 개선 검증(항목 10·11)**: 추측으로 기능을 추가하지 않기
위해, `submission_500.csv`에서 실제로 `NONE`이었던 이미지를 무작위로 84장 뽑아 OCR이 무엇을
읽고 있는지 전수 조사하고 원본 이미지를 눈으로 확인했다. 여기서 "OCR은 날짜를 정확히
읽었는데 파서가 버리는" 두 유형(2자리 연도 / 필드 일부 깨짐)을 발견해 항목 10·11을
구현했다. 검증은 두 단계로 했다: **(a) 단위테스트 41종** — 기존 회귀 케이스 전부와 함께,
이번에 발견한 실제 문자열(`2025.05.0`, `2026.01,00`, `2025.71.10`, `22.10.21`,
`20.12.14 22:54`)과 오탐 위험 케이스(전화번호·영양정보·주소·무게/가격)를 고정했고 전부
통과했다. **(b) 실제 이미지 103장 종단 비교** — 이미지당 OCR을 한 번만 돌려 캐시한 뒤 변경
전/후 파서를 같은 OCR 결과 위에서 각각 실행해 비교했고, **값이 사라지거나 바뀐 이미지 0장,
새로 값이 나온 이미지 8장**으로 회귀 없이 순수 추가임을 확인했다. 실패 표본 84장 기준
복구율은 **7장(8.3%)** 이었고, 여기서 실제 359장 실패분에 적용하면 약 30장이 복구될 것으로
예측했다.

**(5) 최종 버전 500장 재실행 — 예측 검증**: 위 예측이 맞는지 확인하기 위해 항목 10·11을
포함한 최종 코드로 실제 평가 규모(500장) 채점 명령을 같은 4-core 환경에서 다시 실행했다.
결과: **938.4초에 완주, 값이 채워진 행 171/500장(34.2%, `NONE-NONE-NONE` 비율 0.658)** 으로,
개선 전(981.8초, 141장, 0.718) 대비 **정확히 30장을 복구**해 (4)의 예측치와 일치했다.
상대적으로는 성공 행이 21% 늘었다. 시간은 오히려 43초 줄었는데(측정 편차 범위), 파서
오버헤드가 이미지당 0.61ms(500장 전체 0.3초)에 불과해 실행 시간에 영향을 주지 않는다는
사전 측정과 일치한다. 2,400초 컷오프까지 약 1,460초(61%)가 남아 타임아웃 위험은 없다.
(171장은 "연/월/일 중 하나 이상이 확정된 행" 기준이며, 항목 11의 부분 구제로 생긴
`2025-05-NONE` 형태도 포함한다.)

`TIER3_CANVAS_SCHEDULE`의 구체적 임계값은 여전히 로컬 2-core 실측을 기반으로 하며, 위 두
차례(3,352장/500장) 실제 4-core 전체 실행에서 나온 canvas 호출 분포·NONE 사례를 팀이
라벨링해 다음 라운드에 재조정할 계획이다(아래 "알려진 한계" 참고).

### 알려진 한계

- 병뚜껑/캡에 잉크젯으로 각인된 저대비·곡면 인쇄 날짜(예: `2026.07.02`)는 해상도를 높여도
  인식률이 낮다. CLAHE 대비 보정을 적용했지만 완전히 해결되지는 않았다.
- 키워드(`소비기한`/`까지`) 없이 날짜만 단독으로 인쇄된 경우, 다른 숫자(로트번호 등)와 형식이
  같으면 오탐 가능성이 있다. 정규식의 유효 연도 범위(2020~2035) 검증으로 일부를 방어한다.
- 1단계 classical CV가 애초에 후보 박스 자체를 놓치는 경우 3단계(전체 재검출)가 시간이 남을
  때만 복구를 시도한다 — 시간이 빠듯하면 이 경우도 NONE으로 남는다. 팀에서 추가로 라벨링한
  데이터로 박스 검출 규칙을 미세조정하면 3단계에 의존하는 비율 자체를 낮출 수 있다 (향후
  개선 방향).
- `TIER3_CANVAS_SCHEDULE`의 임계값은 여전히 로컬 2-core 환경 실측치를 기반으로 한다. 실제
  4-core 환경에서 3,352장 전체(1,892.8초, 12.14%)와 실제 평가 규모인 500장(981.8초, 28.2%)
  두 스케일 모두로 검증은 마쳤지만, canvas 호출 비율·NONE 사례의 분포를 팀이 라벨링해
  임계값을 데이터 기반으로 재조정하면 추가 개선 여지가 있다 (향후 개선 방향).
- 날짜 표기 순서 판별(항목 8)은 연도(`20\d{2}`)가 이미지 어딘가에 함께 찍혀 있는 경우만
  대응한다. **연도 자체가 아예 인쇄되지 않고 월/일만 있는 경우**(예: `10.14`)는 아직 대응하지
  않는다 — 20xx 같은 뚜렷한 앵커가 없어 무게·가격·전화번호 등과 오탐 구분이 훨씬 어렵기
  때문에, 표본 검수에서 실제 사례를 발견하지 못한 지금 시점에는 구현 우선순위를 낮췄다
  (향후 개선 방향). 구분자 없이 **공백으로만 구분된 2자리 연도**(예: `08 09 21`)도 같은
  이유로 여전히 제외한다 — 구분자가 있는 형태(`22.10.21`)만 항목 10에서 대응한다.
- **실패의 대부분은 파싱이 아니라 "날짜 영역을 아예 못 읽는 것"이다.** 실제 `NONE`이었던
  이미지 84장을 전수 조사한 결과, **79장(94%)은 날짜 비슷한 문자열 자체가 OCR 출력에
  없었다**(상품명·영양정보 같은 다른 텍스트는 잘 읽힘). 즉 남은 개선 여지는 정규식이나
  전처리가 아니라 검출 커버리지 쪽에 있다 — 1단계 박스 제안 규칙 개선, 또는 3단계가 더
  자주/더 큰 canvas로 걸리도록 시간 예산을 재배분하는 방향이 다음 라운드 과제다.
- **시도했으나 효과가 없어 채택하지 않은 것**: dot-matrix/잉크젯 각인 날짜용 모폴로지
  전처리(노이즈 제거 → 점 연결 → 획 두껍게, 구조요소 크기는 글자 높이 비례). 2단계 CLAHE가
  실패한 뒤에만 도는 순수 추가 단계로 구현해 실제 실패 이미지 24장에 A/B로 적용했으나
  **복구 0장**이었고, 실패 이미지당 0.47초만 더 들었다. 위 조사에서 드러났듯 "박스는
  잡혔는데 글자가 뭉개져 못 읽는" 케이스 자체가 표본에 거의 없었기 때문으로 판단해
  제출본에는 반영하지 않았다.
- 바코드(EAN-13) 국가 힌트(항목 9)는 단위테스트(체크섬 검증, 힌트 우선순위 미침범, 실제
  표본 바코드로 애매 사례 해소)와 500장 실제 실행까지 포함해 검증했지만, **이 힌트가 단독으로
  몇 건이나 발동했는지는 따로 계측하지 않았다** — 애초에 관여하는 잔여 애매 케이스 자체가
  드물어(항목 8의 500장 실행에서 5건) 정량적 기여는 작을 것으로 본다. 다만 이미 확정 가능한
  날짜를 절대 덮어쓰지 않도록 설계돼 있어, 기여가 작더라도 정확도를 깎지는 않는다.
