# ITDA 3rd 학술제 제출 저장소 - DScover_카피바라

OCR 기반 상품 소비기한 정보 추출 아키텍처. 자세한 설계 논리는 `[DScover_카피바라]_아키텍처구조도.pdf` (이메일 제출본)를 참고하세요.

## 1. 요약

- **입력**: 상품 뒷면 이미지 (`ITDA_INPUT_DIR` 환경변수로 경로 주입)
- **출력**: `submission.csv` (`ITDA_OUTPUT_PATH` 환경변수 경로에 저장)
- **엔진**: EasyOCR (`ko`+`en`, CPU, 오프라인) + 정규식/키워드 기반 날짜 후보 스코어링
- **핵심 설계**: 1) classical CV 후보 검출 + 배치 인식(1단계) → ROI 재시도(2단계) → 시간이 남을 때만 전체 재검출(3단계)의 3단계 구조, 2) 4-core 병렬처리, 3) 명시적 안전 마진(250초) 기반 시간 예산 가드레일

## 2. 실행 방법

### 1) 환경 구축

```bash
git clone <본인 팀 저장소 URL>
cd itda3-dscover-capybara
pip install -r requirements.txt
```

macOS 사용자는 `requirements.txt` 상단의 `+cpu` 접미사를 제거하고 설치하세요.

### 2) 가중치 다운로드 (인터넷 필요, 1회)

```bash
bash download_weights.sh
```

`weights/craft_mlt_25k.pth`, `weights/korean_g2.pth` 두 파일을 GitHub Release Assets(공식 EasyOCR 저장소)에서 내려받습니다. 이 스크립트는 predict.ipynb 실행 **전에** 1회만 실행하면 되며, predict.ipynb 자체는 `download_enabled=False` 로 동작하여 실행 중 어떤 네트워크 요청도 하지 않습니다.

### 3) 채점 재현성 검증 (운영진 표준 명령어)

```bash
export ITDA_INPUT_DIR=./val_images
export ITDA_OUTPUT_PATH=./submission.csv

jupyter nbconvert --to notebook --execute predict.ipynb \
    --ExecutePreprocessor.timeout=2400 \
    --output /tmp/executed.ipynb
```

오프라인(네트워크 차단) 상태에서도 위 명령이 에러 없이 완료되고 `submission.csv` 가 생성되는지 반드시 확인하세요.

## 3. 아키텍처 설계 논리 (요약)

상품 뒷면에는 소비기한 외에도 제조일자, 바코드, 품목보고번호, 전화번호, 영양성분, LOT 번호 등
날짜와 혼동될 수 있는 숫자가 다수 존재한다. 동시에 채점 환경은 CPU 전용·오프라인·2400초
타임아웃이라는 강한 제약을 가진다.

이 아키텍처는 두 번의 재설계를 거쳤다. 로컬(2-core) 프로파일링만으로는 실제 4-core 채점
환경의 비용 구조를 정확히 예측할 수 없다는 것을 직접 겪었기 때문에, 그 과정을 그대로 남긴다.

**1차 재설계 (로컬 프로파일링 기반, 이후 실제 환경에서 재검증되어 뒤집힘)**: 최초에는
"1단계 classical CV로 저비용 후보 검출 → 실패 시에만 2단계 EasyOCR 전체 파이프라인 fallback"
구조였다. 로컬 2-core에서 150장/60장 표본을 프로파일링한 결과 1단계 적중률이 8~10%에 불과한
반면 처리 시간은 2단계와 비슷해(1.6~1.7초/장), 이미지의 90% 이상이 두 단계 비용을 모두
지불하면서도 이득이 작다고 판단해 1단계를 제거하고 EasyOCR 단일 패스(canvas=550)로
단순화했었다.

**2차 재설계 (실제 4-core 환경 검증 후)**: 실제 채점 환경과 동일한 GitHub Codespaces 4-core
인스턴스에서 전체 3,352장을 직접 실행해보니 위 결론이 뒤집혔다. classical CV 후보 검출을
없애지 않고, 대신 후보 수를 34→16개로 줄이고 실패 시 이미지 전체를 다시 검출하는 대신
상위 6개 후보만 재인식하도록 가볍게 만든 버전이 **전체 3,352장을 1,475.5초 만에 처리하고
(예산 2,250초의 66%만 사용) 성공 378장(11.28%)**을 기록했다 — 이전 단일 패스 방식(9.37%,
게다가 54%만 처리하고 나머지는 시간 초과로 NONE)보다 정확도·커버리지 모두 우수했다. 즉
로컬 2-core와 실제 4-core에서 "classical CV 재사용이 저렴한가"에 대한 결론 자체가 달랐다.
다만 이 방식은 classical CV가 애초에 후보 박스를 놓친 이미지는 구조적으로 복구하지 못한다는
한계가 있었고(로컬 100장 재현 시 확인된 사례: 성공했어야 할 이미지가 이 방식에서는 NONE),
동시에 예산의 34%가 그냥 남는다는 것도 확인됐다. 이에 아래처럼 **3단계 구조**로 다시 합쳤다.

1. **1단계 (classical CV 후보 검출 + 배치 인식)**: 형태학적 연산으로 텍스트 줄 후보를 최대
   16개(`FAST_MAX_BOXES`) 찾고, EasyOCR 검출기(CRAFT)는 생략한 채 인식기만 원본 해상도로
   한 번에 배치 호출한다(`reader.recognize(..., batch_size=...)`). 실제 4-core 환경에서
   대부분의 이미지를 이 단계만으로 매우 저렴하게 처리한다.
2. **2단계 (ROI 재시도)**: 1단계가 실패하면, 이미지 전체를 다시 검출하지 않고 1단계가 찾은
   후보 중 상위 6개(`ROI_RETRY_BOXES`)만 CLAHE로 대비를 보정해 재인식한다. 여전히 저비용이다.
3. **3단계 (전체 재검출, 시간이 남을 때만)**: 1·2단계 모두 실패하면 — classical CV가 애초에
   후보 박스 자체를 놓친 경우라 2단계로는 복구 불가능하다 — **명시적 안전 마진
   (`SAFETY_MARGIN_SEC`=250초)을 침범하지 않는 한도 내에서만** CLAHE + EasyOCR 전체 파이프라인
   (검출+인식)을 다시 시도한다. "워커 1개가 이미지 1장에 쓸 수 있는 여유시간"
   (`(남은 시간×N_WORKERS)/남은 이미지 수`)이 클수록 큰 canvas(550px)를, 작을수록 작은
   canvas(250px)를 쓰고(`TIER3_CANVAS_SCHEDULE`), 그마저 안 되면 3단계를 생략해 NONE으로
   남긴다. 로컬 100장 재현 테스트에서 이 3단계가 1·2단계만으로는 놓쳤던 이미지를 실제로
   복구하는 것을 확인했다(성공 17→30장으로 증가).
4. **후보 스코어링**: 정규식(`YYYY.MM.DD`, `YYYY-MM-DD`, `YYYY년MM월DD일`, 콤마 오인식 보정,
   구분자 없는 `YYYYMMDD` 등)으로 날짜 형식 후보를 모두 추출하고, 달력 기준 유효성 검사
   (`datetime.date`)로 `2026-02-30`처럼 실존하지 않는 날짜를 제외한 뒤, 같은 줄/인접 줄에
   `소비기한`, `유통기한`, `까지` 가 있으면 가점, `제조일자`, `제조`, `LOT` 가 있으면 감점하여
   최고 점수 후보를 최종 날짜로 채택한다. 서로 다른 박스로 쪼개진 날짜 조각은 좌표 기반으로
   이어붙여(stitching) 재시도한다.
5. **4-core 병렬 처리**: `concurrent.futures.ThreadPoolExecutor` 로 이미지 단위 작업을 워커
   스레드에 분배한다. 각 스레드는 최초 호출 시 자신만의 EasyOCR Reader 를 한 번만 로드해
   재사용하며, 프로세스 전체의 BLAS/torch 스레드 수를 1로 고정해(oversubscription 방지)
   워커 수만큼만 코어를 활용한다. `multiprocessing.Pool(fork)` 는 개발 초기에 사용했으나,
   Jupyter 커널(ipykernel)이 이미 여러 백그라운드 스레드를 띄운 상태에서 `fork()` 하면 자식
   프로세스가 락 획득에 실패해 멈추는 사례가 있어 스레드 기반으로 교체했다. 3단계의 여유시간
   계산도 "남은 이미지 수"라는 워커 간 공유 상태가 필요한데, 스레드는 메모리를 공유하므로
   락(`threading.Lock`)으로 보호한 카운터 하나만으로 구현할 수 있었다.
6. **명시적 안전 마진 정책**: "시간이 남으면 정확도에 재투자한다"는 방향을 계속 밀고 나가되,
   `SAFETY_MARGIN_SEC=250초`는 어떤 경우에도 침범하지 않는 하드 하한선으로 둔다. 1·2단계는
   항상 시도하고, 3단계만 이 마진 안에서 남는 시간만큼 적응적으로 수행한다 — 정확도를
   더 올리려는 시도가 "타임아웃으로 정량 0점"이라는 최악의 결과로 이어지지 않도록 하는
   구조적 장치다.
7. **정밀도 우선(NONE 허용) 전략**: 키워드/형식 근거가 불충분한 경우 억지로 추정하기보다 `NONE`
   을 반환하도록 설계했다. 잘못된 날짜를 자신 있게 제시하는 것보다, 근거가 있는 경우에만 값을
   내는 편이 더 신뢰할 수 있는 시스템이라고 판단했기 때문이다.

### 재설계 검증 방법 (재현 가능)

로컬 프로파일링(2-core)과 실제 채점 환경(4-core Codespaces)의 결론이 서로 달랐던 경험 때문에,
이 저장소의 최종 구조는 로컬 표본 추정에만 의존하지 않고 **실제 4-core 환경에서 전체 3,352장을
완주시켜 나온 숫자**(1,475.5초, 성공 378장)를 기준으로 확정했다. 로컬에서는 같은 100장
테스트셋으로 (a) 1·2단계만 있는 버전과 (b) 3단계까지 포함한 버전을 직접 실행해 성공 건수
(17→30장)와 극단적으로 짧은 시간 예산(40초)에서도 안전 마진을 넘기지 않고 완주하는지를
검증했다. `TIER3_CANVAS_SCHEDULE`의 구체적 임계값은 로컬 2-core 실측을 기반으로 하므로, 실제
4-core 환경에서 전체 corpus를 한 번 더 실행해 canvas 분포와 최종 정답률을 확인하고 필요시
재조정하는 절차를 제출 전에 거치는 것을 권장한다.

### 알려진 한계

- 병뚜껑/캡에 잉크젯으로 각인된 저대비·곡면 인쇄 날짜(예: `2026.07.02`)는 해상도를 높여도
  인식률이 낮다. CLAHE 대비 보정을 적용했지만 완전히 해결되지는 않았다.
- 키워드(`소비기한`/`까지`) 없이 날짜만 단독으로 인쇄된 경우, 다른 숫자(로트번호 등)와 형식이
  같으면 오탐 가능성이 있다. 정규식의 유효 연도 범위(2020~2035) 검증으로 일부를 방어한다.
- 1단계 classical CV가 애초에 후보 박스 자체를 놓치는 경우 3단계(전체 재검출)가 시간이 남을
  때만 복구를 시도한다 — 시간이 빠듯하면 이 경우도 NONE으로 남는다. 팀에서 추가로 라벨링한
  데이터로 박스 검출 규칙을 미세조정하면 3단계에 의존하는 비율 자체를 낮출 수 있다 (향후
  개선 방향).
- `TIER3_CANVAS_SCHEDULE`의 임계값은 로컬 2-core 환경 실측치를 기반으로 하므로, 실제 4-core
  채점 환경에서 전체 3,352장을 한 번 더 실행해 3단계 호출 비율·canvas 분포와 최종
  커버리지·정답률을 확인하고 필요시 임계값을 재조정하는 절차를 제출 전에 거치는 것을 권장한다.
