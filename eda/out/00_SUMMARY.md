| 질문 | 실측 답 |
| --- | --- |
| 데이터는 균질한가? | ❌ 해상도 0.29~24.5MP, 640×640이 33%, 출처 최소 2개 |
| OCR이 날짜를 읽는가? | ❌ **56.2%는 날짜를 하나도 못 찾음** (전체 이미지 OCR 기준) |
| 해상도를 올리면 나아지는가? | ❌ 960~3200px **전부 동일** (det 상한 해제 후 재검증) |

**결론: 이 대회의 병목은 후처리 규칙이 아니라 OCR이 날짜를 못 읽는 것(recall)이다.**
전체 이미지를 통으로 OCR 하는 구조로는 상한이 낮다. 날짜 영역을 먼저 찾아 그 crop만
집중 인식하는 2단계 구조가 정확도·속도 양쪽에서 필수다.

## 2. 디코딩 — 확인된 것과 오해하기 쉬운 것

| 항목 | 실측 |
| --- | --- |
| `cv2.imdecode` + `np.fromfile` | 3,352 / 3,352 성공 |
| `PIL.Image.open` | 3,352 / 3,352 성공 |
| MPO 277장 | cv2·PIL 모두 정상 로드, 크기 정합 |

**EXIF 회전은 자동으로 처리된다 (오해 주의).**
`cv2.imdecode`/`imread`는 OpenCV ≥3.4.1부터 EXIF orientation을 **기본 적용**한다.
orientation=6인 293장을 표본 검증한 결과 cv2 결과와 `PIL+exif_transpose` 결과가 전량 일치했다.

- ✅ cv2로 읽으면 별도 처리 불필요
- ⚠️ 단 `PIL.Image.open()` 은 자동 적용하지 않는다 → PIL 경로에서는 `ImageOps.exif_transpose()` 필수
- ⚠️ `cv2.IMREAD_IGNORE_ORIENTATION` 은 절대 켜지 말 것

> 로컬 참고: 프로젝트 경로에 한글이 있어 `cv2.imread(path)` 와 PaddleOCR 모델 로딩이
> 전부 실패한다. 채점 서버 경로(`/eval/val_images`)는 ASCII 라 재현되지 않지만,
> 로컬 실험이 막히므로 `np.fromfile + imdecode` 를 쓰고 모델은 ASCII 경로에 둔다.

## 3. 속도 — 예산을 이미 초과했다

측정 조건: PaddleOCR PP-OCRv3 det + korean PP-OCRv4 rec, CPU, 긴 변 1280px,
4 프로세스 병렬, **AMD Ryzen 5 7500F (6C/12T, 3.7GHz)**

| 항목 | 값 |
| --- | ---: |
| 규정 예산 (2400초 ÷ 3,352장) | **0.72 초/장** |
| 실측 — 1방향 OCR (wall, 4워커) | 0.83 초/장 (**115%**) |
| 실측 — 0°+90° 2방향 (wall, 4워커) | **1.66 초/장 (230%)** |
| 단일 프로세스 1회 중앙값 | 2.67 초 |
| 단일 프로세스 1회 p90 / 최대 | 8.28 초 / 23.23 초 |

> ⚠️ 이 수치는 **낙관적 하한**이다. 측정에 쓴 Zen4 데스크톱 CPU는 채점 환경의
> "Standard 4-Core vCPU"보다 코어당 성능이 높다. 채점 서버에서는 더 느려진다.

**해상도를 낮춰도 검출률이 떨어지지 않는다** (§4 참조) → 다운스케일은 공짜 절감이다.
그러나 그것만으로 230%를 메울 수 없다. 전체 이미지 OCR 구조 자체를 바꿔야 한다.

## 4. 회전 — '고르지 말고 합쳐라'

500장 표본에서 0°와 90° 두 방향을 모두 돌린 뒤 정책을 비교했다.

| 방향 정책 | 날짜 검출 커버리지 | OCR 호출 |
| --- | ---: | ---: |
| 0° 만 | 32.0% | 1회 |
| 점수로 한쪽 선택 | 32.2% | 2회 |
| **0°+90° 합집합** | **43.8%** | 2회 |

> 2회 돌려놓고 한쪽만 채택하면 32.2%로, 0°만 쓴 것과 거의 차이가 없다.
> **두 결과를 합치면 43.8%** — 비용은 동일한데 +11.6%p. **방향 판별기를 만들 이유가 없다.**

육안으로 정답을 확인한 10장 벤치마크에서도 같은 결론이 나왔다.

| 정책 | 적중 | 비고 |
| --- | ---: | --- |
| 0°+90° 합집합 | 5/10 | |
| 0°/90°/180°/270° 합집합 | 6/10 | 비용 2배, +1장 |

- 긴 변 **960px / 1280px / 1600px 결과가 완전히 동일** → 해상도는 병목이 아니다
- 영문 홍차캔(`003341`)은 **180°에서만** 검출 → 방향은 예측 불가
- 성공 케이스는 후보가 항상 1개뿐 → **오탐은 거의 없고, 문제는 순수 recall**

| 앵커 | 장수 | 비율 | 성격 |
| --- | ---: | ---: | --- |
| 까지 | 186 | 37.2% | 보조 |
| 제조일자 | 81 | 16.2% | ❌ 반대 |

| Best Before | 29 | 5.8% | ✅ 정답 |
| 별도표기 | 28 | 5.6% | ⚠️ 함정 |

- 정답 앵커 보유: **27.8%** 뿐
- **앵커가 전혀 없는 이미지: 65.2%** → 위치·형식만으로 판단해야 함
- **정답 앵커와 제조 앵커가 동시에 있는 이미지: 10.0%** → 구분 실패 시 그대로 오답
- `유통기한 제품별도표기일까지` 처럼 **앵커 옆에 날짜가 없는 함정: 5.6%**
  → "앵커에서 가장 가까운 숫자" 규칙은 여기서 무너진다

> 주목: **제조일자(16.2%)가 소비기한(7.4%)보다 많이 등장한다.**
> 앵커를 순진하게 쓰면 오히려 제조일을 집는 쪽으로 편향된다.

## 8. 그래서 무엇을 할 것인가

### 확정된 설계 원칙 (실측 근거 있음)

1. **전체 이미지 통 OCR 구조를 버린다.** 56.2% 미검출 + 예산 230%. 두 문제의 원인이 같다.
   → 날짜 영역 검출 → 해당 crop만 확대 인식하는 2단계 구조.
   전체를 저해상도로 훑어 후보 영역만 고해상도로 재인식하면 정확도·속도가 동시에 개선된다.
2. **다운스케일은 공짜다.** 960px과 1600px의 검출률이 동일 → 1차 스캔은 과감히 낮춘다.
3. **회전은 판별하지 말고 합집합.** 판별기 제작은 비용 대비 효과가 없다(+0.2%p).
4. **후보 선택 규칙**
   - 4자리 연도 우선, 2자리 연도는 앵커 또는 타당 연도 범위 조건부
   - 제조/소비 쌍이면 **더 늦은 날짜**
   - `별도표기` 동반 앵커는 무효화
   - 9자리+ 연속 숫자 내부 매치는 경계 조건으로 원천 차단
   - **미래성 필터 금지** (정답에 2020~2022년이 다수)
5. **제출 형식 방어** — `image_id`는 파일명 문자열 그대로(`000001` ≠ `1`),
   `month`/`day` 2자리 zero-pad, 미인식은 문자열 `NONE`, `index=False`

### 다음 단계

| 우선순위 | 할 일 | 근거 |
| --- | --- | --- |
| 1 | **E등급(미검출) 원인 분해** — 잉크젯/저대비 전처리(CLAHE·이진화·샤프닝) 실험 | 56.2%가 여기 |
| 2 | 날짜 영역 검출기 프로토타입 (경량 det + crop 확대 인식) | 정확도·속도 동시 해결 |
| 3 | 검증셋 200~300장 수동 라벨링 | 현재 정답 10장뿐 — 측정 기반이 너무 얇다 |
| 4 | 후보 선택 스코어링 구현 및 검증셋으로 튜닝 | D등급 4.4% + B등급 29.6% |
| 5 | 채점 명령 그대로 재현한 end-to-end 속도 측정 | 예산 230% 해소 확인 |

### 미해결 / 확인 필요

- **정확도 채점 세부 규칙 미공개** — `final_date` 완전일치인지 `year`/`month`/`day` 부분점수인지에
  따라 전략이 갈린다. 오답 감점 유무(= `NONE`이 유리한지)도 함께 확인 필요 → 오픈채팅 질의
- 평가셋 장수 미공개 — 0.72초/장 예산은 3,352장 가정. 더 적으면 여유가 생긴다
- 640×640 클러스터의 출처 — EXIF가 제거되어 추적 불가
