## 2. 비용이 어디로 가는가 (실측)

1회 통과(0°, det 입력 960px) 분해 — [07_profile.md](eda/out/07_profile.md)

| 단계 | 평균 | 비중 |
| --- | ---: | ---: |
| JPEG 디코딩 | 28 ms | 3.3% |
| 리사이즈 | 2 ms | 0.2% |
| det (검출) | 132 ms | 15.6% |
| **rec (인식)** | **684 ms** | **80.9%** |
| 합계 | 845 ms | 100% |

이미지당 박스 **41개** × 16.6 ms.

> **핵심**: 비용의 5분의 4가 rec 이고, rec 는 박스 수에 정비례한다.
> 그런데 우리가 필요한 박스는 41개 중 **날짜가 든 1~2개**뿐이다.
> 26,499개 박스 중 날짜가 파싱되는 것은 **167개(0.63%)** 에 불과하다.

여기가 이 대회의 CPU 문제를 푸는 지점이다. 모델을 줄이는 게 아니라 **모델을 덜 부르는 것**이다.

## 3. 실측으로 기각된 선택지

값비싼 오답을 미리 걸러냈다. 아래는 전부 **효과가 없다고 측정된** 것들이다.

> ⚠️ **아래 표의 첫 줄은 반쪽짜리 결론이었다.** 해상도를 960px "위로만" 시험했고,
> 아래로 내려가면 오히려 정확도가 오른다는 것을 뒤늦게 발견했다 (§7d).
> 기본값(960)을 검증 범위의 경계로 삼은 것이 실수였다.

| 시도 | 결과 | 판정 |
| --- | --- | --- |
| 입력 해상도 상향 (960→3200px) | recall 5/10 고정, 비용 1.7→2.8초 | ❌ 기각 |
| `det_db_box_thresh` 하향 (0.6→0.15) | recall 5/10 고정 | ❌ 기각 |
| `det_db_unclip_ratio` 상향 (1.5→2.5) | recall 5/10 고정 | ❌ 기각 |
| 2단계 재인식 (박스를 원본 해상도로 재크롭) | 5/10 → 5/10 | ❌ 기각 |
| 방향 판별기 (0°/90° 중 우세한 쪽 선택) | 32.0% → 32.2% | ❌ 기각 |
| **단일 전처리** (이진화·CLAHE·조명평탄화·모폴로지 등 13종) | **n=400 에서 +3.0%p, p=0.201** | ❌ 기각 |
| 축소 디코딩 `IMREAD_REDUCED_COLOR_N` | 11 ms 절감 (1.3%) | △ 미미 |
| 전처리 2개 TTA (합집합) | +10.7%p, 비용 **1.67배** | △ 조건부 |

**전처리 상세** — [17_preprocess_conclusion.md](eda/out/17_preprocess_conclusion.md)

n=100 에서 `adapt_bin` 이 +9.0%p 로 유망해 보였으나 n=400 확정 실행에서 +3.0%p 로
축소되고 유의성을 얻지 못했다(McNemar p=0.201). **+43 얻고 −31 잃는** 패턴이 본질로,
전처리는 성능을 올리는 게 아니라 **어느 이미지가 성공할지를 뒤섞을 뿐**이다.

다만 전 설정 합집합은 52.8%(단일 최고 39.8%)에 달한다. 전처리마다 잡는 이미지가
다르다는 뜻이고, 이는 **det 가 입력의 사소한 변화에 불안정하다**는 신호다.
조합을 늘리는 것보다 안정적인 검출기를 쓰는 편이 낫다.

**해상도 검증 주의**: PaddleOCR 기본값이 `det_limit_side_len=960, det_limit_type='max'` 라
960px 초과 입력은 내부에서 되돌려진다. 처음 측정은 이 상한에 걸린 값이었으나,
상한을 풀고 3200px 까지 올려도 결과가 같아 **해상도가 병목이 아님이 확정**됐다.

**2단계 재인식이 실패한 이유** — 박스 좌표는 정확했지만:
- `001201`(933×701), `003341`(640×640) 은 **원본이 이미 저해상도**라 되돌아갈 화소가 없다
- `000801`, `002401` 은 애초에 **det 가 날짜 영역을 제안하지 않았다** (세로 잉크젯 / 저대비)
- `3352` 는 제조일과 소비기한이 인접해 박스가 뭉개졌다

즉 실패는 세 갈래다: **검출 누락 · 원본 해상도 부족 · 인접 텍스트 간섭**.
셋 다 "더 크게 보기"로는 풀리지 않는다.

## 5. 박스 사전 필터 — CPU 문제의 답

rec 없이 계산 가능한 싸구려 영상 특징만으로 "숫자 줄일 가능성"을 판별한다.
자기지도로 학습·평가했다: rec 를 전부 돌려 날짜가 파싱된 박스를 양성으로 삼고,
이미지 단위 GroupKFold 로 검증. — [08](eda/out/08_boxfilter.md) · [09](eda/out/09_filter_imagelevel.md)

가장 강한 특징 (permutation importance):

| 특징 | 왜 통하는가 |
| --- | --- |
| `aspect` | 날짜줄은 가늘고 길다 |
| `gap_ratio` | 글자 사이 공백 전환 횟수 |
| `cc_h_std` | 숫자는 글자 높이가 균일, 한글은 들쭉날쭉 |
| `cc_ar_mean` | 한글 음절은 정사각, 숫자는 세로로 김 |

### 결과 (이미지 단위)

| 유지 비율 | 1회 통과 | 0°+90° 2회 | **예산 대비** | 이미지 보존율 |
| ---: | ---: | ---: | ---: | ---: |
| 100% (필터 없음) | 830 ms | 1,660 ms | **231%** | 100.0% |
| 40% | 427 ms | 854 ms | **119%** | 94.9% |
| **30%** | **360 ms** | **720 ms** | **100%** | **93.5%** |
| 20% | 293 ms | 586 ms | **81%** | 91.3% |
| 10% | 226 ms | 451 ms | **63%** | 86.2% |

> 상위 30% 만 rec 하면 2회 통과가 정확히 예산 0.72초에 들어온다.
> 대가는 날짜가 잡히던 이미지의 6.5% 손실(138장 중 9장).
> 상위 20% 면 예산의 81% 로 여유가 생기고 손실은 8.7%.

**박스 단위 재현율(89%)보다 이미지 단위 보존율(91%)이 높은 이유**: 같은 날짜가
여러 박스와 두 회전에 중복 등장하므로 양성 박스 몇 개를 놓쳐도 이미지의 날짜는 살아남는다.

> ⚠️ **이 필터는 비용 절감 수단이지 recall 개선 수단이 아니다.**
> rec 가 애초에 못 읽는 날짜는 필터로 살아나지 않는다. 상한은 여전히 34.5% 다.

## 5b. 후처리로 되찾은 recall — 비용 0

10단계 오라클 실험(날짜 위치를 사람이 지정해 주고 인식만 시킨 것)에서
실패가 "못 읽는 것"이 아니라 **"읽어 놓고 놓치는 것"** 인 경우를 찾아냈다.

| 사례 | OCR 실제 출력 | 원인 |
| --- | --- | --- |
| `002401` | `'20221'` + `'104'` | det 가 `2022/11/04` 한 줄을 **두 박스로 분할** |
| `001201` | `'2022716'` | `2022.07.16` 에서 `07` 의 **앞자리 0 탈락** |
| `000801` | `'!"'`, `':'` | 주황 카톤 위 **점(dot) 인쇄** — 판독 불가 |

앞의 둘은 이미 인식된 문자열 안에 답이 있다. 추가 OCR 없이 후처리만으로 복구된다.
— [11_linemerge.md](eda/out/11_linemerge.md), 500장 검증

| 방식 | coverage | Δ | plausible |
| --- | ---: | ---: | ---: |
| 현재 (박스별 엄격 파싱) | 43.8% | — | 91.8% |
| + 인접 박스 병합 | 51.0% | **+7.2%p** | 91.6% |
| + 7자리 느슨 패턴 | 45.8% | +2.0%p | 90.8% |
| **둘 다** | **52.8%** | **+9.0%p** | 90.5% |

> **coverage +9.0%p 를 추론 비용 0 으로 얻는다.** 정밀도 대용 지표는 91.8% → 90.5% 로 사실상 유지.
> 지금까지 시도한 어떤 모델·해상도·임계값 조정보다 큰 이득이며, CPU 예산에 영향이 없다.

구현: `datex.merge_lines()` — 같은 행(세로 중심 차이가 글자 높이의 0.6배 이내)에 있고
가로 간격이 글자 높이의 2배 이내인 박스들의 텍스트를 x 순서로 이어 붙인다.
7자리 패턴은 오탐 위험이 있어 `find_dates(..., loose=True)` 로만 켠다.

## 6. 최종 파이프라인

```
[0] 디코딩          cv2.imdecode(np.fromfile(...))   ← EXIF 회전 자동 적용
[1] 다운스케일      긴 변 960px                       ← 그 이상은 비용만 증가
[2] det (0°)        PP-OCRv3 mobile 검출              ← 132 ms
[2b] 날짜 검출      YOLOv8n(ONNX)이 날짜 영역 제안     ← det 가 놓친 곳 보충, §9
[3] 박스 필터       이미지별 점수 상위 K개만 통과       ← K 는 시간 예산이 정한다
[4] rec             걸러진 박스만 인식
[5] 박스 병합       같은 행·인접 박스 텍스트 결합       ← 비용 0, 정확도 +20%p
[6] 날짜 파싱       구분자 소실 허용 정규식             ← 7자리 느슨 패턴은 기각
      └ 날짜 없으면 → [2] 를 90° 로 1회 더 (적응형)
[7] 후보 선택       4자리 연도 우선 · 동점이면 늦은 날짜
[8] 출력            image_id / year / month / day / final_date
```

> §5 의 "상위 20~30% 고정" 은 §7c 에서 **시간 예산 적응형**으로 대체됐다.
> 고정 필터는 평가셋이 작을 때 정확도를 공짜로 버리기 때문이다.

### [7] 후보 선택 규칙 (실측 근거)

| 규칙 | 근거 |
| --- | --- |
| 4자리 연도 우선 | 정밀도 99.2% (2자리는 79.4%) |
| 2자리 연도는 앵커 또는 타당 연도(2015~2035) 조건부 | `080723`·`411011` 같은 LOT 코드 오탐 |
| 제조/소비 쌍이면 **더 늦은 날짜** | D등급 사례 전부에서 성립 (6·12개월 간격) |
| `별도표기` 동반 앵커는 무효화 | "유통기한 제품별도표기일까지" 함정 5.6% |
| 9자리+ 연속 숫자 내부 매치 차단 | 품목보고번호 `20130628332176` → `2013-06-28` |
| 미래성 필터 **금지** | 정답에 2020~2022년 과거 날짜 다수 |

### 제출 형식 방어

- `image_id` 는 파일명 문자열 그대로 (`000001` ≠ `1`)
- `month`/`day` 2자리 zero-pad, 미인식은 문자열 `NONE`
- `df.to_csv(OUTPUT_PATH, index=False)`
- `requirements.txt` 에 `nbconvert`, `ipykernel` 포함, 버전 고정
- opencv 는 **한 종류만** (headless/contrib/일반 동시 설치 시 numpy ABI 충돌)

## 7b. 실제 정확도 — 대용 지표는 절반만 맞았다

사람이 눈으로 확인한 정답 **34장**으로 처음 진짜 정확도를 쟀다 ([19](eda/out/19_real_accuracy.md)).
그동안 써온 coverage 는 방향은 맞았지만 **채택 판단에는 틀렸다**.

| 방식 | coverage | **accuracy** | 판정 |
| --- | ---: | ---: | --- |
| 박스별 엄격 파싱 (기존) | 52.0% | **48.0%** | 기준선 |
| + 인접 박스 병합 | 72.0% | **68.0%** | ✅ 채택 |
| + 7자리 느슨 패턴 | 64.0% | **48.0%** | ❌ 기각 |
| 병합 + 느슨 | 84.0% | **68.0%** | 느슨은 무의미 |

> **7자리 느슨 패턴은 coverage 를 +12%p 올리면서 정확도는 1건도 못 올렸다.**
> 후보만 늘리는 순수 노이즈였고, coverage 로 판단했다면 채택했을 것이다.
> 반면 박스 병합은 **정확도 +20%p** 로 지금까지의 어떤 수단보다 크다.

선택 규칙은 34장에서 오선택 0건이었다. 정답이 후보에 있으면 항상 골라냈다.

## 7c. 최종 파이프라인 실측 (end-to-end)

채점 명령(`nbconvert --execute`)을 그대로 재현해 측정했다 ([20](eda/out/20_pipeline_eval.md)).

| 박스 필터 | 정확도 (34장) | 3,352장 환산 |
| --- | ---: | ---: |
| 없음 | **64.7%** | 4,176초 ❌ 타임아웃 |
| 상위 40% | 55.9% | 2,276초 |
| 상위 30% | 52.9% | 1,939초 |
| 상위 20% | 50.0% | 1,773초 |

필터는 타임아웃을 막지만 정확도를 크게 깎는다(64.7% → 52.9%).
그런데 **평가셋 장수는 비공개**다. 고정 필터는 둘 중 하나로 틀린다.

- 약하게 → 데이터가 많으면 타임아웃, 정량 60점이 통째로 0
- 세게 → 데이터가 적으면 정확도를 공짜로 버린다

그래서 **시간 예산 적응형**을 택했다. 필터 없이 최고 정확도로 시작하고,
25장마다 예상 완주 시간을 계산해 예산(2,100초)을 넘길 것 같으면 그때부터 조인다.

```
keep 사다리: None → 0.60 → 0.40 → 0.30 → 0.20 → 0.12
여유가 예산의 55% 미만으로 돌아오면 다시 완화한다
```

동작 검증 (100장, 예산 45초로 강제):

```
[budget] keep -> 0.6 at 25/100
[budget] keep -> 0.4 at 50/100
[budget] keep -> 0.3 at 75/100
done: 100 rows in 90s (0.900s/img)     ← 1.31 → 0.90 s/img
```

작은 평가셋에서는 사다리가 한 칸도 내려가지 않아 64.7% 정확도를 그대로 쓴다.

### 두 가지 버그를 실측으로 잡았다

**1. 전역 임계값 방식의 박스 필터는 무너진다.**
학습 데이터 분위수로 임계값을 정했더니 정확도가 **22/34 → 13/34** 로 붕괴했다.
학습 시와 추론 시 점수 분포가 어긋나면 임계값이 통째로 밀리기 때문이다.
**이미지별 상위 K개**로 바꾸자 예측대로 동작했다(자기정규화되어 분포 이동에 무관).

**2. 2자리 연도 후보의 타당성 검사가 없었다.**
`000429` 에서 LOT 코드가 `2041-04-14` 로 파싱되어 유일 후보가 되는 바람에
그대로 출력됐다. 2자리 연도 패턴은 정밀도가 79.4% 뿐이므로
**연도가 2015~2035 를 벗어나면 후보에서 제거**하도록 고쳤다. 오탐이 사라졌다.

(정확도 손실이 작거나 없다), 그 다음에 박스 필터와 두 번째 패스를 줄인다
(정확도 손실이 크다).

   IoU 1.000 으로 일치함을 확인했다. `requirements.txt` 에 torch 를 넣으면 안 된다.

### 속도 기록 정정

기존 문서의 "0.99초/장, 제한의 21%" 는 **4프로세스 병렬 처리량**을 잘못 쓴 값이다.

설정 간 *비교* 에는 기존 표를 그대로 써도 되지만, 절대 예산에는 이 값을 써야 한다.

## 9c. 본선 고도화 — 계단 구조 (2026-09-25)

전체 기록은 [JOURNAL.md §12d](JOURNAL.md), 최종 판정은
[eda/out/96_holdout4_eval.md](eda/out/96_holdout4_eval.md).

### 설계 원칙: 재시도는 실패분에만

이번 라운드의 모든 추가는 같은 모양이다. **이미 실패한 이미지에만 다음 칸을
돌린다.** 그러면 맞히던 것을 건드릴 수 없으므로 회귀가 구조적으로 0 이고,
비용도 실패한 몇 %에만 든다.

```
[1] det small @1024        82%가 여기서 끝난다 (중앙값 0.40초)
[2] adaptive threshold
[3] det medium             실패분에만
[4] CLAHE + det medium     실패분에만
[5] rec 한국어             실패분에만 — 한글이 날짜에 붙어 있는 경우
[6] rec 영문               실패분에만
[7] 도트 판독기(CTC)       실패분에만 — 점으로 찍힌 날짜
[8] 보조 경로 PP-OCR+YOLO   그래도 실패한 것만
    ↳ 어느 칸도 온전한 날짜를 못 내면, 그제서야 부분 결과를 쓴다
```

전면 교체를 하지 않은 이유는 실측이다. det medium 을 처음부터 쓰면 라벨
179장에서 85.1% → 89.4% 로 오르지만 **맞히던 2장을 망가뜨린다**(EDA 74~75).
계단으로 걸면 그 회귀가 사라지고 미검출만 줄어든다.

### 가장 큰 이득은 새 모델이 아니라 버그 수정이었다

`_from_texts` 가 완전한 날짜를 못 만들면 **부분 결과**를 냈는데, 부분 결과도
`None` 이 아니라서 계단이 거기서 멈췄다. 다음 칸이 온전한 날짜를 읽을 수 있는
이미지가 반쪽짜리에 머물렀다. `002335` 는 OCR 이 `2021.11.19` 를 정확히 읽고도
출력이 `NONE-11-19` 였다.

각 칸이 **완전한 날짜만** 성공으로 치고 부분 결과는 마지막에만 쓰도록 고쳤다.
잃는 것 없이 580장에서 6장을 얻었다. 이 한 줄이 이번 라운드에서 가장 큰
단일 기여다.

### 규칙에 보탠 것

| 보탠 것 | 근거 |
| --- | --- |
| `DD MON YYYY` · `MON DD YY` | `01 SEP 2023` `JUL 22 21` 이 어느 패턴에도 안 걸렸다 |
| `YYYYMM.DD` | `202512.20m` — 구분자가 뒤에만 있는 모양이 빠져 있었다 |
| 날짜 뒤 `:숫자` 차단 | `2026.08` + `22:14` 에서 **시각이 일(日)로 먹혔다** |
| 2자리 연도 한국식 기본 | 유럽식 52% vs 한국식 91% (EDA 81) |

월 이름이 있으면 월 자리가 확정되므로 첫 두 개는 오탐 위험이 낮다.

### 측정에서 배운 것

**진단은 파이프라인과 같은 순서로 재현해야 한다.** 여러 칸의 텍스트를 합쳐서
보면 파이프라인이 본 적 없는 정보를 봤다고 착각한다. 이 실수로 "규칙으로 15장
고칠 수 있다"는 결론이 나왔는데, 계단을 그대로 재현하니 **실제로는 2장**이었다
(EDA 89 → 90). 나머지 49장은 OCR 이 글자를 못 만드는 경우다.

**눈에 띄는 것과 원인은 다르다.** 오답 사진에서 흐릿한 것이 눈에 띄었지만,
선명도를 재니 오답(중앙값 458)이 정답 표본(412)보다 오히려 또렷했다.
이 신호로는 가를 수 없다.

### 인식기가 한글을 못 읽고 있었다

주력 인식기 `PP-OCRv6_rec_small` 은 중국어 모델이다. 날짜는 숫자라 읽지만
한글이 날짜에 **바로 붙어 있으면**(`나 2026.03.11 까지 홍병현`, `유통2023.01.05까지`)
그 글자를 엉뚱한 한자로 읽으면서 날짜까지 함께 깨뜨린다.

| 인식기 | 같은 이미지에서 읽은 것 |
| --- | --- |
| rec_small | `内213-3，` `苦号卫电立20130628332176` |
| **rec_korean** | `별자치도 제주시 첨단로 213-3,` `품목보고번호 20130628332176` |

이것이 규칙의 점수 체계가 놀고 있던 이유이기도 하다. `유통기한`·`까지`·`제조일`
같은 키워드가 깨져 들어오니 모든 후보가 0점이 되고, 동점일 때 "늦은 날짜"를
고르는 규칙만 남았다. 인식기를 바꾼 칸을 계단 끝에 붙여 해결했다.

### 도트 인쇄는 전용 판독기를 따로 학습했다

남은 미검출이 거의 전부 **도트 매트릭스 인쇄**였다. 인식기가 `26.08.13` 을
`2:88:13` 으로 읽는다. 전처리 문제가 아니라 **그 글꼴을 학습한 적이 없는** 것이다.

도트 인쇄는 일반 글자를 점 격자로 샘플링한 것과 같으므로, 일반 폰트로 날짜를
그린 뒤 점 마스크를 씌워 학습 데이터를 합성했다. 글자를 하나씩 잘라 분류하는
방식은 **여덟 글자가 전부 맞아야 해서** 실패했고(정답 0장), CTC 시퀀스 모델로
줄 단위 판독으로 바꾸니 풀렸다.

YOLO 도 도트용으로 파인튜닝해 봤으나 **잡던 것을 놓쳐 순손해**라 기각했다.

### 그런데 병목은 도트도, 검출도 아니었다

판독기를 다 만든 뒤에 **정말 도트가 문제인지** 828장 전량에서 쟀다. 그전까지는
미검출 12장만 보고 판단한 것이었다.

| 갈라 본 기준 | 결과 |
| --- | --- |
| 도트 인쇄 대 일반 인쇄 | **97.0% 대 95.9%** — 도트가 오히려 더 잘 읽힌다 |
| YOLO 검출 성공 대 실패 | 96.1% 대 85.8% (**−10.2%p**) |

두 번째가 병목처럼 보였다. 왜 못 잡는지 찾으려 날짜 위치를 OCR 박스에서
역산해 비교했는데 크기(0.90배)·대비(1.05배)·위치(0.91배) **어느 것도 두 무리를
가르지 못했다.** 지표가 같은데 한쪽만 못 잡는다면 남는 설명은 하나다 —
**확신이 낮아 버려지고 있다.** 실제로 `conf` 를 0.25→0.02 로 내리니 못 잡던
193장 중 **80%** 가 잡혔다. 학습 데이터가 238장뿐이니 그럴 만하다.

**그런데 고쳐도 정확도가 오르지 않았다.** `conf=0.05` 로 248장을 다시 재니
92.3% → 92.2%, 744필드 중 1개 차이였다. 홀드아웃4 는 +2필드, 홀드아웃5 는
−3필드로 **방향조차 갈렸다** — 한쪽만 봤다면 "+0.4%p 개선"으로 채택했을 것이다.

이 기각이 결과보다 크다. **−10.2%p 는 상관을 인과로 읽은 것이었다.** YOLO 가
못 잡는 이미지는 애초에 작고 흐리고 기울어져 있어 **읽기도** 어렵다. 검출
실패가 성능을 떨어뜨린 것이 아니라 둘 다 같은 원인의 결과였다. 검출을 강제로
성공시켰는데 결과가 안 움직인 것이 그 증거다.

> 방법론으로 남긴 것: **하위 그룹의 성능 차이는 그 자체로 원인을 지목하지**
> **않는다.** 원인이라고 주장하려면 그 변수를 직접 건드려 결과가 따라오는지
> 봐야 한다. 이 프로젝트는 병목을 두 번 잘못 짚었고, 두 번 다 오답만이 아니라
> **양쪽을 재는** 것으로 드러났다.

속도는 두 가지 방식으로 쟀고 **보수적인 쪽을 보고한다.**

**503초 / 21%** 를 쓴다. 어느 쪽이든 제한의 5분의 1 수준이다.

> 노트북을 채점 조건으로 끝까지 돌려 본 것은 결함 하나를 잡아냈기 때문에도
> 중요했다. **PaddleOCR 은 비ASCII 경로의 모델을 열지 못하고, 조용히 실패한다.**
> 실험 스크립트는 ASCII 경로에서 모델을 읽어 이 문제를 비켜 가고 있었다.
> 경로가 비ASCII 면 ASCII 임시 폴더로 복사해 넘기도록 고쳤다(JOURNAL.md 참고).

라벨 580장에서 잰 값은 94.1% 였다. 그 표본은 오답을 한 장씩 들여다보며
고쳤으므로 **1.8%p 가 낙관 편향**이다. 보고에는 92.3% 를 쓴다.
